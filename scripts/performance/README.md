# 批量性能与正确性验证

项目根目录只需一个入口：

```sh
npm run validate -- --postgres --performance --large --output /tmp/sheetforge-validation
```

需要 Python 3.12+、Node、Rust、`cargo-audit`、Docker、`/usr/bin/time`。依赖先执行 `npm ci`。默认运行格式、Clippy、Rust、审计、前端测试与生产构建；`--postgres` 自动启动仅绑定本机随机端口的临时 PostgreSQL 17，测试后删除。不会连接业务数据库。

`--performance` 在临时源目录注入同一份 ignored 测量入口，分别按旧提交与当前源码的锁文件构建 release 测试程序；不会修改旧分支。固定同批输入，逐环节三次对照，记录源文件 SHA-256、源码指纹、工具链、耗时、进程峰值 RSS；源行流、预览、导出读回内容逐格分帧哈希核验，输出还比较工作表和样式 XML。行流计时包含内容哈希成本。超过 10% 的耗时/内存变化会在 JSON 标出，必须结合原因审核；去重落盘属于内存与速度的明确取舍，不能把不同输出或跳过数据当成提速。

矩阵包括千行、万行、百万行，16/64/256/512 列，GBK、共享字符串、偏移标题与 8 Sheet、100 个异名字段来源、复杂数值边界；`--large` 追加千万行一次正确性/压力验证，不从这一次测量作性能结论。复杂值含长编号、极大/极小数、精度边界、布尔、毫秒日期、多行与转义、空值和重复行。普通测试不会生成大文件。

预览 `_warm` 表示同一进程已完成扫描，计时不含扫描准备，RSS 包含准备；这符合导入后手动点预览的流程。`cached` 另测已读样本再次请求。文件系统缓存不强制清空，不能等同冷盘或 Windows 完整桌面时间。报告允许在源指纹和输入不变时继续未完成的阶段；修改源码后必须换输出目录。`--rerun-cases 名称...` 只重测指定场景，`--rerun-stages 场景:环节...` 可只补测受干扰的环节，保留同一批生成文件。

前端元数据在同一 Node/Vue 进程中批量测首次分组、单表编辑重算和序列化。脚本还构建新旧生产版浏览器测试页，分别提供 `frontend-performance/{baseline,current}-ui/scripts/performance/index.html`。使用本机静态服务器打开，点一次“运行全部界面测试”完成三种宽度各三次挂载、分页搜索/编辑焦点，以及当前版千来源合并预览滚动、末列、固定来源、空表、窗口缩放检查。旧版千来源界面没有虚拟化，跳过该压力场景，避免创建几百万个 DOM；不计为通过。该页面不进入应用入口。浏览器结果、Windows CI 与本机引擎测量应分别报告。

每个阶段单独保留日志，失败只输出末尾；`validation.json`、`matrix.json` 为汇总。可分别运行 `python3 scripts/performance_matrix.py ...` 或 `python3 scripts/performance_frontend.py ...` 定位已确认的失败，无需重做无关检查。

压缩等级 3/6 作为 `cfg(test)` 实验保留，不暴露到生产界面。完整导出收益不足 10%，且文件体积增加，本轮不增加快速导出选项。
